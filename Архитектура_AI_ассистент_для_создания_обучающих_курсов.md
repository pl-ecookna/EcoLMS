# Архитектурный документ
## Проект: AI-ассистент для создания обучающих курсов

**Версия:** 1.0  
**Дата:** 2026-04-06

---

## 1. Архитектурные цели

Архитектура системы должна обеспечить:
1. загрузку больших файлов через единый веб-интерфейс;
2. устойчивую обработку долгих задач в фоне;
3. отделение stateful-инфраструктуры от redeploy приложения;
4. поэтапную полуавтоматическую генерацию материалов;
5. хранение промежуточных и итоговых артефактов в Markdown и JSON;
6. возможность дальнейшего масштабирования тяжелых этапов обработки.

---

## 2. Принятые архитектурные решения

### 2.1. Базовые решения
1. Приложение строится как набор сервисов.
2. PostgreSQL и Redis размещаются отдельно от основного deployment.
3. S3-хранилище используется как внешний объектный сторедж.
4. Основное приложение деплоится через Dokploy.
5. Прямая загрузка файлов выполняется из браузера в Beget S3-compatible storage.
6. Для больших файлов используется multipart upload.
7. Фоновая обработка реализуется через очередь задач.
8. FFmpeg не выносится в самостоятельный сетевой сервис, а устанавливается внутри worker-контейнера.
9. Сервис транскрибации выделяется отдельно и использует `openai/whisper`.

## 5. Декомпозиция сервисов

## 5.1. Frontend
### Ответственность
- аутентификация пользователя;
- выбор локальных файлов;
- показ прогресса загрузки;
- запуск обработки;
- отображение статусов;
- просмотр и редактирование результатов этапов;
- скачивание Markdown и JSON артефактов.

### Что не делает
- не проксирует большие файлы через backend;
- не выполняет тяжелую обработку;
- не хранит бизнес-данные.

---

## 5.2. Backend API
### Ответственность
- аутентификация и авторизация;
- выдача данных для direct upload в S3;
- orchestration multipart upload;
- регистрация файлов и проектов в БД;
- постановка задач в очередь;
- выдача статусов;
- прием и сохранение пользовательских правок;
- выдача ссылок/метаданных на артефакты.

### Что не делает
- не выполняет транскрибацию;
- не запускает FFmpeg;
- не извлекает документы напрямую.

---

## 5.3. Worker
### Ответственность
- забирать job из очереди;
- скачивать исходные файлы из S3;
- выполнять preprocessing;
- запускать FFmpeg;
- извлекать текст из документов;
- вызывать transcription service;
- вызывать LLM-провайдер для нормализации и генерации;
- сохранять артефакты в S3;
- обновлять статусы и результаты в PostgreSQL.

### Почему FFmpeg внутри worker
Такой подход проще и дешевле для MVP:
- меньше сетевых hops;
- меньше внутренних API;
- одна точка выполнения media pipeline;
- при росте нагрузки можно вынести целый media-worker позже.

---

## 5.4. Transcription service
### Ответственность
- принимать аудиофайлы или пути к ним;
- запускать `openai/whisper`;
- возвращать транскрипт и, при реализации, сегменты/таймкоды;
- работать как изолированный ресурсноемкий сервис.

### Почему отдельный сервис
В отличие от FFmpeg, транскрибация — отдельный тяжелый вычислительный этап, который выгодно изолировать:
- проще масштабировать;
- проще заменить реализацию позже;
- проще контролировать ресурсы и лимиты.

## 6. Архитектура загрузки больших файлов

## 6.1. Выбранный вариант
**Direct-to-S3 multipart upload из браузера.**

### Причины выбора
1. Не требуется проксировать гигабайты данных через backend.
2. Снижается нагрузка на API-сервис.
3. Поддерживается загрузка крупных файлов.
4. При сбое можно перезагрузить только проблемные части.
5. Пользователь получает единый интерфейс без CLI и внешних утилит.

## 6.2. Техническая схема загрузки
1. Frontend запрашивает у API создание upload-сессии.
2. API регистрирует файл в БД.
3. API инициирует multipart upload в Beget S3-compatible storage.
4. API возвращает браузеру данные для загрузки частей.
5. Frontend загружает части файла напрямую в S3.
6. После завершения частей frontend вызывает API для finalize.
7. API завершает multipart upload и обновляет статус файла.

## 6.3. Ограничения загрузки
- до 2 ГБ на файл;
- до 5 файлов;
- базовые ретраи только в рамках текущей сессии браузера;
- без восстановления после закрытия вкладки.

## 7. Архитектура очередей и фоновой обработки

## 7.1. Причины использования очереди
Очередь нужна, потому что:
- загрузка и обработка разнесены по времени;
- видео и документы обрабатываются долго;
- тяжелые задачи нельзя выполнять синхронно в HTTP-запросе;
- необходимо управлять повторами, ошибками и статусами.

## 7.2. Логика работы
1. API создает запись проекта и файлов.
2. После подтверждения обработки API ставит job в очередь.
3. Worker забирает job.
4. Worker выполняет этап.
5. После завершения этапа worker либо:
   - переводит проект в `awaiting_review_*`,
   - либо запускает следующий внутренний технический этап.

## 7.3. Предлагаемые очереди
- `project-processing`
- `media-preprocessing`
- `document-extraction`
- `transcription`
- `llm-normalization`
- `llm-outline`
- `llm-content`
- `llm-test`

Для MVP допустимо начать с одной основной очереди и типизации jobs по полю `stage`.


## 9. Артефакты и их хранение

## 9.1. Принцип хранения
Все промежуточные и итоговые артефакты хранятся в S3.
В PostgreSQL хранятся только:
- метаданные;
- статусы;
- ссылки/ключи объектов;
- результаты выполнения задач;
- ссылки на актуальные версии артефактов.

## 9.2. Группы артефактов
### Исходные
- загруженные пользователем файлы

### Технические
- извлеченное аудио
- временные результаты извлечения текста
- raw transcript

### Пользовательские промежуточные
- source_compiled.md/json
- course_outline.md/json
- course_content.md/json
- course_test.md/json

### Финальные
- утвержденные версии markdown/json по каждому этапу

## 9.3. Рекомендация по ключам хранения
```text
projects/{project_id}/sources/{file_id}/...
projects/{project_id}/artifacts/{stage}/{filename}
projects/{project_id}/tmp/{job_id}/...
```

## 11. Состояния проекта

Предлагаемая state machine:

```text
uploading
→ uploaded
→ queued
→ preprocessing
→ transcribing / extracting_documents
→ normalizing
→ awaiting_review_source
→ generating_outline
→ awaiting_review_outline
→ generating_content
→ awaiting_review_content
→ generating_test
→ awaiting_review_test
→ completed
```

Ветвь ошибки:

```text
any_state → failed
```

Дополнительно:
- `retryable_failed` — опционально на этапе реализации;
- `cancelled` — опционально, не обязателен для MVP.

## 12. Обработка ошибок

## 12.1. Ошибки загрузки
- сбой части multipart upload;
- несоответствие размера/типа файла;
- ошибка finalize upload.

### Реакция
- показать ошибку пользователю;
- дать возможность повтора части/повтора загрузки файла.

## 12.2. Ошибки медиаобработки
- поврежденный видеофайл;
- нераспознаваемая аудиодорожка;
- ошибка FFmpeg.

### Реакция
- пометить этап как failed;
- сохранить технический лог;
- дать возможность повторить этап.

## 12.3. Ошибки транскрибации
- падение сервиса транскрибации;
- превышение времени обработки;
- невалидный результат.

### Реакция
- повтор job по политике retry;
- при окончательном падении — статус failed.

## 12.4. Ошибки LLM-этапов
- невалидный JSON;
- пустой результат;
- сетевой сбой API.

### Реакция
- повтор с лимитом попыток;
- сохранение ошибки в job log;
- перевод этапа в failed.

## 13. Безопасность

## 13.1. Общие принципы
1. Секреты передаются только через env-переменные.
2. Frontend не получает постоянные credentials S3.
3. Для загрузки используются временные/подписанные данные.
4. Backend проверяет доступ пользователя к проекту.
5. Нужно ограничить допустимые типы и размеры файлов.

## 13.2. Сетевые границы
- frontend доступен пользователю;
- api доступен frontend;
- worker и transcription service могут быть недоступны извне;
- PostgreSQL и Redis должны быть доступны только приложению по внутренним правилам доступа.

## 14. Деплой и эксплуатация

## 14.1. Разделение сервисов
### Внешние сервисы
- PostgreSQL
- Redis
- Beget S3

### Сервисы приложения
- frontend
- api
- worker
- transcription-service

## 14.2. Почему external Postgres/Redis — правильное решение
1. Redeploy приложения не затрагивает данные БД и очереди.
2. Stateful-компоненты отделены от stateless-логики.
3. Проще обслуживать резервное копирование и мониторинг.
4. Проще заменять или обновлять контейнеры приложения.

## 14.3. Dokploy deployment model
В Dokploy основное приложение разворачивается как multi-service stack.
При redeploy могут пересоздаваться контейнеры frontend/api/worker/transcription-service, но данные во внешних PostgreSQL, Redis и S3 не затрагиваются.

## 15. Производительность и масштабирование

## 15.1. Горячие точки нагрузки
1. Загрузка крупных файлов.
2. Извлечение аудио FFmpeg.
3. Транскрибация через Whisper.
4. Длинные LLM-этапы генерации.

## 15.2. Стратегия MVP
- один экземпляр API;
- один экземпляр frontend;
- один или ограниченное число worker-процессов;
- один экземпляр transcription-service.

## 15.3. Масштабирование на вырост
### Вертикальное
- увеличить CPU/RAM worker и transcription-service.

### Горизонтальное
- добавить worker replicas;
- при необходимости выделить transcription-service на отдельную машину.

### Что пока не масштабируется отдельно
- ffmpeg как самостоятельный сетевой сервис не выделяется.

## 19. Риски и меры снижения

## 19.1. Риск: длительная обработка длинных видео
**Мера:** фоновые очереди, статусы, retry, ограничение до 3 часов как рекомендуемый предел.

## 19.2. Риск: высокое потребление ресурсов транскрибацией
**Мера:** отдельный transcription-service, возможность вынесения на отдельный хост.

## 19.3. Риск: нестабильная загрузка больших файлов
**Мера:** multipart upload, прогресс, retry частей, валидация до запуска обработки.

## 19.4. Риск: потеря данных при redeploy
**Мера:** вынесенные PostgreSQL, Redis и S3, отсутствие хранения stateful-данных внутри контейнеров приложения.

## 19.5. Риск: невалидные результаты генерации
**Мера:** промежуточные JSON-артефакты, ручное подтверждение между этапами, валидация результата до перехода дальше.

## 20. Итоговая рекомендованная схема MVP

```text
[Browser / Frontend]
   ├─ direct multipart upload ───────────────→ [Beget S3]
   └─ HTTPS ─────────────────────────────────→ [API]
                                                ├─ PostgreSQL (external)
                                                ├─ Redis / BullMQ (external)
                                                └─ enqueue jobs

[Worker]
   ├─ download files from S3
   ├─ FFmpeg preprocessing
   ├─ document text extraction
   ├─ call transcription-service
   ├─ call LLM provider
   ├─ save artifacts to S3
   └─ update statuses in PostgreSQL

[Transcription Service]
   └─ openai/whisper
```

Это решение является рекомендуемой архитектурой для MVP и соответствует следующим ограничениям:
- внутренний инструмент;
- один пользовательский тип;
- загрузка больших файлов через единый интерфейс;
- локальная транскрибация на русском языке;
- поэтапная полуавтоматическая генерация;
- deploy через Dokploy;
- stateful-инфраструктура вынесена отдельно.
