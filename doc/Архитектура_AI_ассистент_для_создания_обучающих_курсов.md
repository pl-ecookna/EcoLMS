# Архитектурный документ
## Проект: AI-ассистент для создания обучающих курсов

**Версия:** 1.1  
**Дата:** 2026-04-06

---

## 1. Цель архитектуры

Архитектура должна обеспечить:

1. прямую загрузку больших файлов из браузера в S3-compatible storage;
2. устойчивую фоновую обработку длинных задач;
3. поэтапную генерацию курса с ручным подтверждением результата;
4. хранение итоговых и промежуточных артефактов в S3;
5. простую эксплуатацию в одном Dokploy-проекте на одном сервере;
6. возможность дальнейшего роста без перестройки всего решения.

---

## 2. Зафиксированные решения

1. Приложение разворачивается как один Dokploy project на одном сервере.
2. Frontend, API, worker и transcription service входят в один stack.
3. PostgreSQL, Redis и S3 остаются внешними сервисами.
4. Аутентификация в MVP не нужна.
5. В одном проекте можно смешивать видео и документы.
6. У upload нет восстановления после закрытия вкладки браузера.
7. Редактирование этапов выполняется в обычном Markdown-редакторе.
8. Подтверждение этапа происходит на том же экране, где редактируется результат.
9. LLM-провайдеры для MVP: OpenAI и OpenRouter.
10. Canonical job status model: `queued`, `processing`, `done`, `failed`.
11. Имя проекта берется из GitHub-источника и не задается вручную.
12. В системе хранится только последняя версия отредактированного этапа.

## 4. Общая схема

```text
Пользователь
   ↓
Frontend (Next.js + shadcn/ui)
   ↓

   ↓

Worker (Python + FFmpeg + LLM clients)
```

## 5. Роли сервисов

### 5.1. Frontend

Frontend отвечает за:

- создание и просмотр проектов;
- загрузку файлов напрямую в S3;
- отображение прогресса загрузки;
- запуск обработки;
- просмотр статуса проекта и задач;
- редактирование Markdown-результатов;
- подтверждение этапов;
- скачивание итоговых артефактов.

Frontend не должен:

- проксировать большие файлы через backend;
- выполнять тяжелую обработку;
- хранить бизнес-логику генерации.

### 5.2. Backend API

Backend API отвечает за:

- создание и обновление проектов;
- выдачу параметров multipart upload;
- регистрацию upload sessions;
- запуск обработки;
- выдачу статусов и метаданных;
- сохранение правок и подтверждений этапов;
- формирование ссылок на артефакты.

Backend API не должен:

- запускать FFmpeg;
- выполнять транскрибацию;
- извлекать тексты из документов;
- генерировать образовательный контент.

### 5.3. Worker

Worker отвечает за:

- забор задач из очереди;
- скачивание исходников из S3;
- preprocessing;
- извлечение текста из документов;
- извлечение аудио из видео;
- нормализацию аудио;
- вызов transcription service;
- вызов LLM-провайдеров;
- сохранение артефактов в S3;
- обновление статусов в PostgreSQL.

### 5.4. Transcription service

Transcription service отвечает только за:

- прием аудиофайла или ссылки на файл;
- запуск `openai/whisper`;
- возврат текста и, если доступно, сегментов;
- изоляцию ресурсоемкой транскрибации от worker.

## 6. Загрузка файлов

### 6.1. Выбранный подход

Используется direct-to-S3 multipart upload из браузера.

### 6.2. Причины

1. Большие файлы не проходят через backend.
2. API не перегружается потоками данных.
3. Пользователь получает прогресс и ретраи частей.
4. Для MVP не нужен resume после закрытия вкладки.

### 6.3. Поток загрузки

1. Frontend создаёт проект.
2. Backend регистрирует upload session.
3. Backend выдаёт данные для multipart upload.
4. Frontend загружает части напрямую в S3.
5. После завершения frontend вызывает complete.
6. Backend завершает multipart upload и помечает файл как `uploaded`.

### 6.4. Ограничения

- до 2 ГБ на файл;
- до 5 файлов в одном проекте;
- только текущая браузерная сессия;
- без обязательного восстановления после закрытия вкладки.

## 7. Очереди и фоновые задачи

### 7.1. Зачем нужна очередь

Очередь нужна для:

- отделения upload от обработки;
- поддержки долгих задач;
- контроля повторов;
- фиксации статусов;
- последовательного прохождения этапов.

### 7.2. Логика

1. Пользователь завершает загрузку.
2. Пользователь запускает обработку проекта.
3. API ставит задачу в очередь.
4. Worker обрабатывает проект по этапам.
5. После каждого этапа проект переходит в режим ручной проверки.
6. Следующий этап запускается только после подтверждения пользователя.

### 7.3. Очередь MVP

Для MVP достаточно одной очереди `project-processing` с полем `stage`.

## 8. Пайплайн обработки

### 8.1. Видео

```text
S3 video
→ download to worker scratch space
→ ffprobe / validation
→ ffmpeg extract audio
→ normalize audio
→ transcription service
→ raw_transcript artifacts
→ source_compiled artifacts
```

### 8.2. Документы

```text
S3 document
→ download to worker
→ extract text
→ normalize text blocks
→ source_compiled artifacts
```

### 8.3. Генерация курса

```text
source_compiled
→ course_outline
→ user review
→ course_content
→ user review
→ course_test
→ user review
→ final artifacts
```

## 9. Форматы и артефакты

### 9.1. Обязательные артефакты

- `source_compiled.md`
- `source_compiled.json`
- `course_outline.md`
- `course_outline.json`
- `course_content.md`
- `course_content.json`
- `course_test.md`
- `course_test.json`

### 9.2. Дополнительные артефакты для видео

- `raw_transcript.md`
- `raw_transcript.json`

### 9.3. Правило хранения

Большие результаты хранятся в S3. В PostgreSQL сохраняются только метаданные, ссылки и короткие служебные поля.

### 9.4. Очистка артефактов

1. Очистка S3 выполняется раз в неделю.
2. Удалять можно только артефакты проектов, для которых уже собран полный пакет:
   - `course_outline`;
   - `course_content`;
   - `course_test`.
3. До сборки полного пакета исходные и промежуточные артефакты не удаляются.
4. Для полного пакета можно дополнительно применять срок хранения, но только при соблюдении условия полноты пакета.

## 10. Статусы

### 10.1. Job statuses

- `queued`
- `processing`
- `done`
- `failed`

### 10.2. Project statuses

- `draft`
- `uploaded`
- `processing`
- `awaiting_review`
- `completed`
- `failed`

### 10.3. Привязка статусов к этапам

Этапы обработки:

- `source_compiled`
- `course_outline`
- `course_content`
- `course_test`

Stage review хранится отдельно от job status и фиксирует, что результат был отредактирован и подтвержден пользователем.

## 11. Обработка ошибок

### 11.1. Upload

- ошибка части multipart upload;
- превышение размера;
- неподдерживаемый MIME type;
- ошибка complete.

### 11.2. Видео и документы

- поврежденный файл;
- неподдерживаемый формат;
- ошибка FFmpeg;
- ошибка извлечения текста.

### 11.3. Transcription

- недоступен сервис;
- ошибка модели;
- невалидный результат;
- таймаут.

### 11.4. LLM

- ошибка сети;
- пустой результат;
- невалидный JSON.

### 11.5. Реакция

- сохранять технический лог;
- помечать job как `failed`;
- позволять повторить этап.

---

## 12. Безопасность

1. Секреты передаются только через env-переменные.
2. Frontend не получает постоянные S3 credentials.
3. Backend проверяет размеры и типы файлов.
4. Доступ к backend, worker и transcription service не должен быть публичным без необходимости.
5. Upload осуществляется через временные или подписанные данные.

## 13. Деплой

### 13.1. Среда

- сервер заказчика в Beget;
- деплой через Dokploy;

### 13.2. Сервисы

- frontend;
- backend API;
- worker;
- transcription service;
- PostgreSQL;
- Redis.

### 13.3. Поведение при redeploy

Redeploy не должен удалять данные в PostgreSQL, Redis и S3.

---

## 14. Нагрузка и масштабирование

Проект рассчитан на небольшой внутренний контур:

- до 5 пользователей;
- до 100 генераций в месяц.

Это означает, что приоритет у простоты и надежности, а не у сложной горизонтальной масштабируемости.
