# Модуль `meetings`

**Статус:** backend API, схема БД, worker pipeline и UI-раздел `/meetings` реализованы  
**Дата фиксации:** 2026-04-18

Документ собирает значимые решения по отдельному модулю анализа записей встреч. Он основан на исходном ТЗ и на последующих проектных решениях, принятых в рабочем обсуждении.

## 0. Текущий статус реализации

На текущий момент в кодовой базе уже реализованы:

- backend-таблицы `meetings`, `meeting_source_files`, `meeting_upload_sessions`, `meeting_jobs`, `meeting_speakers`, `meeting_speaker_segments`, `meeting_artifacts`
- REST API `/api/meetings/*`
- отдельная Redis-очередь `ecolms:meeting-jobs`
- worker pipeline:
  - `audio_prepared`
  - `transcript_compiled`
  - `meeting_summary`
  - `meeting_protocol`
  - `meeting_actions`
- интеграция worker с `SaluteSpeech` через async API
- нормализация diarized transcript в PostgreSQL и генерация meeting artifacts

Интеграционные проверки (локально, 2026-04-18):

- подтверждён e2e-прогон `meetings` до стадии `transcript_compiled` на реальных `SaluteSpeech` credentials
- проверена загрузка файла через `/api/meetings/:id/uploads/*` и запуск через `/api/meetings/:id/start`
- подтверждена нормализация diarized transcript в `meeting_speakers` и `meeting_speaker_segments`
- ранее блокер на LLM-стадиях (`CERTIFICATE_VERIFY_FAILED`) устранён в worker:
  - для OpenAI/OpenRouter используется trust store из `certifi`
  - после фикса подтверждено прохождение стадий `meeting_summary|meeting_protocol|meeting_actions` до `done`
- UI-модуль `/meetings` добавлен:
  - двухпанельный рабочий экран в стиле курсов: слева список встреч, справа результаты обработки
  - карточка встречи с diarized transcript
  - ручная правка speaker labels
  - единый markdown-файл на встречу
  - просмотр job-истории и артефактов
  - отдельная страница встречи `/meetings/[id]` для прямых ссылок и точечного просмотра

Подготовка runtime для `worker`, уже зафиксированная в репозитории:

- локальный запуск worker стандартизирован через `uv`
- docker-образ worker включает `ffmpeg` и `ca-certificates`
- compose-конфигурации прокидывают `WORKER_MEETING_JOB_QUEUE_KEY` и `SALUTESPEECH_*`

Проверки, которые уже выполнены:

- `pnpm --dir apps/api build`
- `python3 -m py_compile apps/worker/src/worker/main.py`

Ограничение локальной проверки:

- прямой import worker-модуля в системном `python3` сейчас упирается в отсутствие пакета `psycopg` в этом окружении; это ограничение локального runtime, а не синтаксическая ошибка модуля

## 1. Позиционирование модуля

- `meetings` — отдельный bounded context внутри EcoLMS
- модуль не смешивается с workflow генерации курсов
- у модуля будут свои:
  - сущности БД
  - API
  - UI
  - worker pipeline
- при этом он переиспользует общую инфраструктуру:
  - PostgreSQL
  - Redis
  - S3-compatible storage
  - `web`
  - `api`
  - `worker`

## 2. Зафиксированные продуктовые решения

- язык встреч в V1: только русский
- одна встреча = один исходный файл
- поиск и фильтрация по транскрипту в V1 не нужны
- speaker labels должны редактироваться пользователем в UI
- `summary`, `protocol`, `actions` генерируются только из diarized transcript
- `actionItems` должны по возможности включать:
  - `assignee`
  - `deadline`
  если эти данные явно прозвучали на встрече
- markdown остаётся пользовательским форматом чтения и редактирования
- JSON используется как структурированное представление и формат обмена, но не как единственный источник истины

## 3. Решение по распознаванию и диаризации

### 3.1. Целевой провайдер

В V1 единственным целевым провайдером выбран `SaluteSpeech`.

Причины:

- встречи только на русском языке
- у проекта нет GPU-инфраструктуры
- нужен баланс между качеством и операционной сложностью
- managed-сервис снижает риск сложной self-host поддержки diarization pipeline

### 3.2. Что не делаем в V1

- не делаем benchmark между несколькими провайдерами
- не проектируем multi-provider abstraction как обязательную часть архитектуры
- не делаем self-host diarization основным сценарием

### 3.3. Техническое решение по входу в провайдер

В `SaluteSpeech` отправляется не исходное видео, а нормализованное аудио.

Канонический поток:

1. загрузить исходный `video/audio` файл в S3
2. на нашей стороне извлечь аудио через `ffmpeg`
3. подготовить аудио в подходящем формате для `SaluteSpeech`
4. отправить аудио в `SaluteSpeech`
5. сохранить сырой ответ провайдера в `meeting_jobs.result_json`
6. нормализовать diarized transcript в собственную схему БД

## 10. Worker pipeline для `meetings`

Ниже зафиксирован целевой pipeline V1 для backend и worker.

### 10.1. Общий сценарий

1. пользователь создаёт встречу
2. загружает один исходный файл
3. backend завершает multipart upload и переводит встречу в `uploaded`
4. пользователь запускает анализ
5. `api` ставит job в очередь Redis
6. `worker` подготавливает аудио и отправляет его в `SaluteSpeech`
7. `worker` получает diarized transcript
8. `worker` нормализует результат в таблицы `meeting_speakers` и `meeting_speaker_segments`
9. `worker` последовательно генерирует:
   - `meeting_summary`
   - `meeting_protocol`
   - `meeting_actions`
10. результат сохраняется в `meeting_artifacts`

### 10.2. Стадии jobs

В V1 используются такие стадии `meeting_jobs`:

- `audio_prepared`
- `transcript_compiled`
- `meeting_summary`
- `meeting_protocol`
- `meeting_actions`

Стадии `transcription` и `diarization` не выносятся в отдельные бизнес-этапы. Они считаются внутренней частью шага `transcript_compiled`, потому что:

- у нас один целевой провайдер
- пользователю важен именно готовый diarized transcript
- это упрощает retry и UI

### 10.3. Подготовка аудио

На вход модуль может получить `video/*` или `audio/*`, но в `SaluteSpeech` всегда отправляется подготовленный аудиофайл.

Целевой формат подготовки:

- контейнер: `ogg`
- кодирование: `OPUS`
- целевая частота подготовки: `48 kHz`
- канальность: всегда `mono` для V1 diarization-пайплайна

Основание для выбора:

- `SaluteSpeech` поддерживает `OPUS`
- для асинхронного распознавания поддерживаются длинные и многоканальные аудиозаписи
- `speaker separation` доступен для модели `general`

Это следует из официальной документации `SaluteSpeech`:

- асинхронное распознавание подходит для многоканальных аудиозаписей и файлов до 1 Гб
- `OPUS` поддерживается для async-распознавания
- разделение спикеров доступно только для модели `general`

Источники:

- [Асинхронное распознавание SaluteSpeech](https://developers.sber.ru/docs/ru/salutespeech/guides/recognition/recognition-async)
- [Допустимые форматы и лимиты](https://developers.sber.ru/docs/ru/salutespeech/guides/recognition/encodings)
- [Как улучшить распознавание](https://developers.sber.ru/docs/ru/salutespeech/guides/recognition/improvement)

### 10.4. Решение по интеграции с `SaluteSpeech`

Для V1 целевым вариантом считается асинхронное распознавание.

Канонический сценарий вызова:

1. получить access token
2. загрузить подготовленный аудиофайл в хранилище `SaluteSpeech`
3. создать асинхронную задачу распознавания
4. периодически запрашивать статус задачи
5. после завершения скачать JSON-файл результата

Основание:

- запись встреч длинная, синхронный REST режим не подходит
- `SaluteSpeech` явно рекомендует async для длинного аудио
- нам не нужны промежуточные realtime-результаты

### 10.5. Параметры распознавания

В запросе к `SaluteSpeech` для V1 фиксируются такие намерения:

- язык: русский
- акустическая модель: `general`
- включено разделение спикеров
- в `options` используется `speaker_separation_options.enable=true` (актуальный REST-параметр)
- формат аудио в запросе: `audio_encoding=OPUS`

Важно:

- поддержка русского языка для async-распознавания документирована
- `speaker separation` доступен только для модели `general`

Если в будущем появятся дополнительные опции качества или хинты, их можно расширить без изменения модели данных.

Технический нюанс текущей интеграции:

- `data:download` может возвращать JSON-массив чанков, а не только JSON-объект;
- в этих чанках идентификатор спикера приходит в `speaker_info.speaker_id`, поэтому нормализация должна учитывать split: `speaker_info` + `results[*]`.

### 10.6. Что хранится в `meeting_jobs.result_json`

`meeting_jobs.result_json` сохраняет сырой ответ `SaluteSpeech` без потери значимых полей.

Минимум сохраняем:

- исходный `task_id` или аналогичный идентификатор задачи провайдера
- идентификатор файла результата провайдера
- полный JSON результата распознавания
- служебные метаданные запроса:
  - язык
  - модель
  - факт включённого speaker separation
  - путь к подготовленному аудио в нашем S3

Это нужно для:

- аудита
- разборов качества
- повторной нормализации без повторного вызова провайдера

### 10.7. Нормализация diarized transcript

Официальная документация `SaluteSpeech` указывает, что при включённом разделении спикеров в результате появляется `speaker_id`.

Правило нормализации:

- `speaker_id = -1` считаем агрегированным или общим результатом
- его не используем как канонический speaker segment
- канонический transcript строим только из сегментов/реплик, где speaker определён явно

Если в ответе есть несколько уровней данных, используем приоритет:

1. сегменты или реплики с speaker attribution
2. слова с таймкодами, если требуется собрать сегменты вручную
3. общий текст только как fallback для технической диагностики

### 10.8. Mapping в наши таблицы

#### `meeting_speakers`

Для каждого уникального `speaker_id` из результата `SaluteSpeech` создаётся speaker:

- `speaker_label = speaker_<id>`
- `display_name = Спикер <n>`
- `is_user_edited = false`

`sort_order` определяется по первому появлению спикера в транскрипте.

#### `meeting_speaker_segments`

Для каждого diarized сегмента создаётся запись:

- `meeting_id`
- `speaker_id`
- `speaker_label`
- `start_ms`
- `end_ms`
- `text`
- `confidence`
- `provider_payload_json`

Правила:

- `start_ms` и `end_ms` всегда приводятся к миллисекундам
- пустые сегменты не сохраняются
- соседние сегменты одного спикера можно склеивать только если они непосредственно смежные и это не ухудшает читаемость

#### `meeting_artifacts` для transcript

После нормализации создаются два артефакта стадии `transcript_compiled`:

- `md`
- `json`

`transcript_compiled.md` строится в читабельном виде:

```md
## [00:00:01 - 00:00:05] Спикер 1
Текст реплики.
```

`transcript_compiled.json` собирается из нормализованных speakers и segments, а не хранится как сырой ответ провайдера.

### 10.9. Канонический JSON transcript

Нормализованный JSON transcript для нашего модуля должен иметь форму:

```json
{
  "meetingId": "meet_123",
  "speakers": [
    {
      "id": "spk_1",
      "speakerLabel": "speaker_1",
      "displayName": "Спикер 1",
      "isUserEdited": false,
      "sortOrder": 1
    }
  ],
  "segments": [
    {
      "id": 101,
      "speakerId": "spk_1",
      "speakerLabel": "speaker_1",
      "displayName": "Спикер 1",
      "startMs": 1200,
      "endMs": 5400,
      "text": "Коллеги, начинаем встречу.",
      "confidence": 0.92
    }
  ]
}
```

Этот JSON:

- формируется из нашей БД
- используется в UI и экспорте
- не зависит напрямую от формата `SaluteSpeech`

### 10.10. Генерация summary, protocol, actions

После успешного `transcript_compiled` worker последовательно запускает:

1. `meeting_summary`
2. `meeting_protocol`
3. `meeting_actions`

Во все три генерации подаётся только нормализованный diarized transcript.

Нельзя использовать:

- исходный сырой текст без спикеров как основной источник
- внешние знания о встрече
- догадки о неозвученных решениях, сроках и ответственных

### 10.11. Источники для LLM

LLM получает:

- markdown transcript
- при необходимости нормализованный JSON transcript

Рекомендуемое правило:

- `summary` и `protocol` строятся в первую очередь из markdown transcript
- `actions` строятся из transcript плюс опора на `sourceSegmentIds`

### 10.12. Правила для `meeting_actions`

При генерации `meeting_actions` worker должен извлекать:

- `decisions`
- `actionItems`
- `openQuestions`

Для `actionItems`:

- `assignee` заполняется только если явно назван
- `deadline` заполняется только если явно прозвучал
- `sourceSegmentIds` обязателен, если удалось однозначно определить опорные сегменты

### 10.13. Обновление статусов встречи

Правила обновления `meetings.status`:

- `draft` — встреча создана, файл не загружен
- `uploaded` — файл загружен, анализ ещё не запускался
- `processing` — есть активный job
- `completed` — transcript и производные артефакты успешно собраны
- `failed` — текущий pipeline завершился ошибкой

Дополнительно обновляются:

- `duration_seconds`
- `speakers_count`
- `processing_started_at`
- `processing_finished_at`
- `error_text`

### 10.14. Retry-логика

Для V1 retry выполняется на уровне `meeting_jobs`.

Правила:

- `audio_prepared` можно повторять безопасно
- `transcript_compiled` можно повторять безопасно с полной перезаписью transcript artifacts и segments
- `meeting_summary`, `meeting_protocol`, `meeting_actions` можно повторять независимо

При повторе `transcript_compiled` нужно:

- удалить старые `meeting_speaker_segments`
- пересобрать `meeting_speakers`
- пересоздать transcript artifacts

### 10.15. Что не делаем в V1

- не редактируем текст сегментов вручную
- не делаем merge/split сегментов через UI
- не делаем автоматическое объединение speaker identities поверх провайдерного результата
- не поддерживаем альтернативных провайдеров в основном pipeline

### 10.16. Следующий шаг реализации

После этого проектного шага можно переходить к реализации:

1. схема БД и миграция `meetings`
2. backend endpoints `/api/meetings/*`
3. worker integration с `SaluteSpeech`
4. UI списка и карточки встреч

## 11. Переменные окружения для `meetings`

Для worker pipeline модуля `meetings` используются такие переменные окружения:

- `WORKER_MEETING_JOB_QUEUE_KEY`
- `SALUTESPEECH_AUTH_KEY`
- `SALUTESPEECH_OAUTH_URL`
- `SALUTESPEECH_REST_URL`
- `SALUTESPEECH_UPLOAD_URL`
- `SALUTESPEECH_RECOGNIZE_URL`
- `SALUTESPEECH_TASK_URL`
- `SALUTESPEECH_DOWNLOAD_URL`
- `SALUTESPEECH_SCOPE`
- `SALUTESPEECH_MODEL`
- `SALUTESPEECH_LANGUAGE`
- `SALUTESPEECH_CA_CERT_PATH`
- `SALUTESPEECH_SSL_NO_VERIFY`
- `SALUTESPEECH_POLL_INTERVAL_SECONDS`
- `SALUTESPEECH_TIMEOUT_SECONDS`

Рекомендации для V1:

- `SALUTESPEECH_MODEL=general`
- `SALUTESPEECH_LANGUAGE=ru-RU`
- в провайдер отправляется подготовленный `wav` с `PCM_S16LE`
- для длинных встреч используется async-распознавание
- для TLS к Sber предпочтительно использовать `SALUTESPEECH_CA_CERT_PATH=certs/russiantrustedca.pem`
- в dev-среде при TLS-проблемах можно временно использовать `SALUTESPEECH_SSL_NO_VERIFY=true`
