# EcoLMS. Документация для заказчика

**Дата актуализации:** 2026-04-28  
**Назначение документа:** описание текущей реализации EcoLMS для бизнес-пользователей и ИТ-службы заказчика.

## 1. Назначение системы

EcoLMS — внутренняя платформа для подготовки обучающих материалов и обработки записей встреч на основе файлов заказчика.

Система закрывает два основных сценария:

- создание обучающих курсов из документов, презентаций, текстовых файлов, аудио и видео;
- анализ записей встреч с получением транскрипта, краткой сводки, протокола, решений и поручений.

EcoLMS рассчитана на работу с корпоративными материалами заказчика. Пользователь загружает исходные файлы, запускает обработку, проверяет и редактирует результаты в интерфейсе. Тяжёлая обработка выполняется фоновым worker-процессом.

## 2. Роли и зоны ответственности

### Бизнес-пользователь

Работает через web-интерфейс:

- создаёт курсы и встречи;
- загружает исходные материалы;
- запускает генерацию;
- просматривает статус обработки;
- редактирует итоговые markdown-материалы;
- копирует или скачивает результаты.

### Администратор / ИТ-служба

Отвечает за эксплуатацию:

- доступность сервисов `web`, `api`, `worker`, `transcription-service`;
- PostgreSQL, Redis и S3-compatible storage;
- переменные окружения и секреты провайдеров;
- LLM-провайдер OpenAI или OpenRouter;
- AssemblyAI для распознавания русскоязычных встреч, SaluteSpeech сохранён как альтернативный STT-провайдер;
- диагностику через health-check, логи и статусы фоновых задач;
- обновление промптов через административный экран.

В текущей реализации встроенной аутентификации и разграничения прав нет. Если система публикуется за пределами доверенного контура, доступ должен ограничиваться средствами инфраструктуры: VPN, reverse proxy, SSO, Basic Auth или другим внешним механизмом.

## 3. Технический стек

### Frontend

- Next.js `16.2.2`
- React `19.2.4`
- TypeScript `5`
- Tailwind CSS `4`
- shadcn/ui
- `react-markdown`, `remark-gfm`
- `lucide-react` для иконок

Frontend расположен в `apps/web` и использует Next.js App Router. Для UI используются компоненты shadcn/ui.

### Backend API

- NestJS `11`
- TypeScript
- PostgreSQL driver `pg`
- `class-validator`, `class-transformer`

Backend расположен в `apps/api`. Все внешние маршруты доступны под префиксом `/api`.

### Фоновая обработка

- Python `>=3.12`
- `psycopg`
- `boto3`
- `pypdf`
- `python-docx`
- `python-pptx`
- `striprtf`
- `certifi`
- `ffmpeg` в runtime worker-контейнера

Worker расположен в `apps/worker`. Он читает задания из Redis, скачивает файлы из S3-compatible storage, извлекает текст, вызывает LLM и сохраняет результаты в PostgreSQL.

### Транскрибация

- Python `>=3.12`
- `faster-whisper`
- `boto3`
- `ffmpeg`

Сервис расположен в `apps/transcription-service`. Он используется существующим pipeline курсов для аудио и видео.

### Инфраструктура

- PostgreSQL `16`
- Redis `7`
- S3-compatible object storage
- Docker Compose / Dokploy для развёртывания

### Внешние ML/AI-провайдеры

- OpenAI или OpenRouter для генерации текстовых артефактов;
- AssemblyAI для распознавания и диаризации русскоязычных встреч, SaluteSpeech как альтернативный провайдер.

## 4. Архитектура сервисов

```text
Browser
  -> web (Next.js)
  -> api (NestJS, /api)
     -> PostgreSQL
     -> Redis
     -> S3-compatible storage

worker (Python)
  -> Redis
  -> PostgreSQL
  -> S3-compatible storage
  -> transcription-service
  -> OpenAI / OpenRouter
  -> AssemblyAI / SaluteSpeech

transcription-service (Python)
  -> S3-compatible storage
  -> faster-whisper
```

Основной принцип архитектуры: web-интерфейс не обрабатывает файлы самостоятельно. Он создаёт сущности, загружает файлы и показывает результаты. API управляет данными и очередями. Worker выполняет длительные операции асинхронно.

## 5. Пользовательский интерфейс

### 5.1. Основной LMS-интерфейс курсов

Главный экран доступен по маршруту `/`.

Функции:

- просмотр списка курсов с пагинацией;
- создание нового курса;
- загрузка до 5 исходных файлов при создании;
- поддержка документов, презентаций, текстов, аудио и видео;
- просмотр статусов курса и отдельных этапов;
- запуск генерации по этапам;
- просмотр и редактирование результата в Markdown;
- сохранение отредактированного артефакта;
- добавление файлов в существующий курс;
- удаление исходных файлов;
- удаление курса;
- просмотр health-статуса сервисов в верхней части экрана;
- переход к модулю встреч и редактору промптов.

Этапы курса:

- `Источник` (`source_compiled`) — сбор и очистка исходных материалов;
- `План курса` (`course_outline`) — структура будущего курса;
- `Обучающие материалы` (`course_content`) — основной учебный контент;
- `Тест` (`course_test`) — проверочные вопросы.

Поддерживаемые расширения при создании курса:

- документы и тексты: `pdf`, `ppt`, `pptx`, `doc`, `docx`, `txt`, `md`, `rtf`;
- аудио: `mp3`, `wav`, `m4a`, `aac`, `ogg`, `flac`;
- видео: `mp4`, `mov`, `avi`, `mkv`, `webm`, `mpeg`, `mpg`.

### 5.2. Интерфейс обработки встреч

Раздел встреч доступен по маршруту `/meetings`.

Функции:

- просмотр списка встреч;
- создание новой записи встречи;
- загрузка одного файла встречи;
- автоматический запуск обработки после загрузки;
- просмотр прогресса по стадиям;
- просмотр итогового Markdown с секциями сводки, протокола и поручений;
- просмотр diarized transcript;
- ручная правка отображаемых имён спикеров;
- повторная генерация материалов после правки спикеров;
- копирование Markdown;
- скачивание Markdown;
- просмотр технической информации, jobs и артефактов в панели `Информация`;
- удаление встречи;
- открытие отдельной страницы встречи по прямой ссылке `/meetings/[id]`.

Этапы обработки встречи:

- `Аудио` (`audio_prepared`) — подготовка аудио из исходного файла;
- `Транскрипт` (`transcript_compiled`) — распознавание и диаризация;
- `Сводка` (`meeting_summary`) — краткое содержание;
- `Протокол` (`meeting_protocol`) — протокол встречи;
- `Действия` (`meeting_actions`) — решения, поручения и открытые вопросы.

В версии V1 модуль встреч рассчитан на русский язык. Одна встреча соответствует одному исходному файлу.

### 5.3. Редактор промптов

Редактор доступен по маршруту `/prompts`.

Назначение:

- просмотр промптов модулей `LMS` и `Meetings`;
- редактирование названия промпта;
- редактирование `system prompt`;
- редактирование `user prompt template`;
- сохранение изменений без деплоя кода.

Промпты хранятся в PostgreSQL в таблице `llm_prompts`. При пустой таблице система создаёт начальные значения из seed-набора backend-кода.

Редактор промптов является административной функцией. Изменение промптов влияет на последующие генерации.

## 6. Административный и эксплуатационный интерфейс

### Health-check

API предоставляет endpoint:

```text
GET /api/health
```

Он возвращает сводный статус:

- `api`;
- `postgres`;
- `redis`;
- `llm`;
- `speechProvider`;
- `worker`;
- `transcriptionService`;
- счётчики проектов и upload-сессий.

Web-интерфейс показывает этот статус в виде health badge на экранах LMS и встреч, а имя активного STT-провайдера приходит отдельно в health payload.

### Очереди обработки

Используются Redis lists:

- `ecolms:processing-jobs` — задачи курсов;
- `ecolms:meeting-jobs` — задачи встреч.

Статусы задач хранятся в PostgreSQL в таблицах `processing_jobs` и `meeting_jobs`.

### Диагностика

При разборе инцидентов рекомендуется проверять в таком порядке:

1. `/api/health`;
2. статус `web`, `api`, `worker`, `transcription-service`;
3. подключение к PostgreSQL;
4. подключение к Redis;
5. наличие и корректность S3-переменных;
6. записи `processing_jobs` или `meeting_jobs`;
7. `error_text` в задачах и сущностях проекта/встречи;
8. логи worker;
9. доступность OpenAI/OpenRouter;
10. доступность и квоты SaluteSpeech для встреч.

## 7. Модель данных

Источник истины для прикладных данных — PostgreSQL. Object storage используется для исходных файлов и multipart upload.

### 7.1. Курсы

#### `projects`

Основная карточка курса.

Ключевые поля:

- `id`;
- `name`;
- `github_ref`;
- `source_summary`;
- `status`;
- `current_stage`;
- `progress`;
- `files`;
- `overview`;
- `stage_drafts`;
- `logs`;
- `created_at`;
- `updated_at`.

Статусы:

- `draft`;
- `uploaded`;
- `processing`;
- `awaiting_review`;
- `completed`;
- `failed`.

#### `source_files`

Исходные файлы курса.

Ключевые поля:

- `project_id`;
- `original_name`;
- `mime_type`;
- `size_bytes`;
- `storage_key`;
- `upload_status`;
- `processing_status`;
- `kind`;
- `position`.

#### `upload_sessions`

Сессии multipart upload для файлов курса.

Ключевые поля:

- `project_id`;
- `source_file_id`;
- `s3_upload_id`;
- `status`;
- `bucket`;
- `storage_key`;
- `original_name`;
- `mime_type`;
- `size_bytes`;
- `kind`.

#### `processing_jobs`

Фоновые задачи курсов.

Ключевые поля:

- `project_id`;
- `stage`;
- `status`;
- `payload_json`;
- `result_json`;
- `error_text`;
- `started_at`;
- `finished_at`;
- `created_at`.

Этапы:

- `source_compiled`;
- `course_outline`;
- `course_content`;
- `course_test`.

#### `artifacts`

Результаты генерации курсов.

Ключевые поля:

- `project_id`;
- `stage`;
- `format`;

- `content_json`;

- `updated_at`.

Таблица для фиксации подтверждения этапов. В схеме и store-слое она есть, но публичный HTTP endpoint подтверждения этапа в текущей версии не опубликован.

#### `meetings`

Основная карточка встречи.

Ключевые поля:

- `id`;
- `title`;
- `description`;
- `status`;

- `speakers_count`;
- `processing_started_at`;

- `error_text`;

Статусы:

- `uploaded`;
- `processing`;
- `completed`;
- `failed`.

Исходный файл встречи.

Ключевые поля:

- `size_bytes`;
- `storage_key`;
- `upload_status`;

- `audio_mime_type`.

Ограничение: одна встреча может иметь только один исходный файл.

#### `meeting_upload_sessions`

Сессии multipart upload для файла встречи.

Ключевые поля:

- `meeting_id`;
- `source_file_id`;
- `s3_upload_id`;
- `status`;
- `bucket`;
- `storage_key`;
- `original_name`;
- `mime_type`;
- `size_bytes`.

#### `meeting_jobs`

Фоновые задачи встреч.

Ключевые поля:

- `meeting_id`;
- `stage`;
- `status`;
- `payload_json`;
- `result_json`;
- `error_text`;
- `started_at`;
- `finished_at`;
- `created_at`.

Этапы:

- `audio_prepared`;
- `transcript_compiled`;
- `meeting_summary`;
- `meeting_protocol`;
- `meeting_actions`.

Сырой ответ выбранного STT-провайдера сохраняется в `result_json` соответствующей задачи.

#### `meeting_speakers`

Справочник спикеров внутри встречи.

Ключевые поля:

- `meeting_id`;
- `speaker_label`;
- `display_name`;
- `is_user_edited`;
- `sort_order`.

`speaker_label` — системная метка провайдера, `display_name` — имя, которое редактирует пользователь.

#### `meeting_speaker_segments`

Канонический diarized transcript.

Ключевые поля:

- `meeting_id`;
- `speaker_id`;
- `speaker_label`;
- `start_ms`;
- `end_ms`;
- `text`;
- `confidence`;
- `provider_payload_json`.

#### `meeting_artifacts`

Результаты обработки встречи.

Ключевые поля:

- `meeting_id`;
- `stage`;
- `format`;
- `content_md`;
- `content_json`;
- `created_at`;
- `updated_at`.

Форматы:

- `md` — человекочитаемый результат;
- `json` — структурированное представление для решений, поручений и служебных данных.

### 7.3. Промпты

#### `llm_prompts`

Редактируемые шаблоны промптов.

Ключевые поля:

- `module`;
- `prompt_key`;
- `title`;
- `system_prompt`;
- `user_prompt_template`;
- `created_at`;
- `updated_at`.

Допустимые модули:

- `lms`;
- `meetings`.

Первичный ключ: `module`, `prompt_key`.

## 8. API

Подробное описание API хранится в [API_описание.md](/Users/romangaleev/CodeProject/Ecookna/EcoLMS/doc/API_описание.md).

Основные группы маршрутов:

- `/api/health` — состояние сервисов;
- `/api/projects/*` — курсы;
- `/api/projects/{id}/uploads/*` и `/api/uploads/*` — загрузка файлов курсов;
- `/api/projects/{id}/artifacts/*` — артефакты курсов;
- `/api/projects/{id}/jobs/*` — задачи курсов;
- `/api/meetings/*` — встречи;
- `/api/meeting-uploads/*` — загрузка файлов встреч;
- `/api/meetings/{id}/transcript` — транскрипт встречи;
- `/api/meetings/{id}/segments` — сегменты транскрипта;
- `/api/meetings/{id}/artifacts/*` — артефакты встреч;
- `/api/meetings/{id}/jobs/*` — задачи встреч;
- `/api/prompts/*` — управление промптами.

Успешные ответы API возвращаются в envelope:

```json
{
  "success": true,
  "data": {},
  "error": null
}
```

## 9. Переменные окружения

Полный пример находится в [.env.example](/Users/romangaleev/CodeProject/Ecookna/EcoLMS/.env.example).

Ключевые группы переменных:

- порты: `WEB_PORT`, `API_PORT`, `TRANSCRIPTION_PORT`;
- адрес backend для web: `ECOLMS_API_BASE_URL`;
- PostgreSQL: `POSTGRES_URL`;
- Redis: `REDIS_URL`;
- S3-compatible storage: `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`;
- LLM: `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `LLM_PRIMARY_PROVIDER`, `OPENAI_MODEL`, `OPENROUTER_MODEL`, `LLM_TIMEOUT_SECONDS`;
- transcription-service: `TRANSCRIPTION_SERVICE_URL`, `WHISPER_MODEL_SIZE`, `WHISPER_COMPUTE_TYPE`;
- очереди: `WORKER_JOB_QUEUE_KEY`, `WORKER_MEETING_JOB_QUEUE_KEY`;
- STT-провайдер: `MEETING_TRANSCRIPTION_PROVIDER`, `ASSEMBLYAI_*`, `SALUTESPEECH_*`.

Секреты нельзя сохранять в коде, документации репозитория или коммитах. Для production следует использовать секреты Dokploy или другой механизм секретного хранения.

## 10. Локальный запуск

```bash
pnpm install
pnpm dev:infra:up
pnpm dev:api
pnpm dev:web
pnpm dev:worker
pnpm dev:transcription
```

Основные команды:

- `pnpm dev:web` — frontend;
- `pnpm dev:api` — backend API;
- `pnpm dev:worker` — worker;
- `pnpm dev:transcription` — transcription-service;
- `pnpm build` — сборка `web` и `api`;
- `pnpm lint` — lint frontend;
- `pnpm docker:up` — запуск Docker Compose;
- `pnpm docker:down` — остановка Docker Compose.

## 11. Ограничения текущей реализации

- встроенной аутентификации и ролевой модели нет;
- модуль встреч V1 рассчитан на русский язык;
- одна встреча поддерживает один исходный файл;
- поиск по транскрипту встречи в текущей версии не реализован;
- публичный endpoint подтверждения этапа курса пока не опубликован;
- очередь реализована через Redis list без BullMQ;
- `pnpm build` собирает `web` и `api`, Python-сервисы запускаются отдельно;
- доступность LLM и активного STT-провайдера зависит от внешних провайдеров, квот и баланса.
