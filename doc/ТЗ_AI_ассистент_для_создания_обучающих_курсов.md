# Техническое задание
## Проект: AI-ассистент для создания обучающих курсов

**Версия:** 1.1  
**Дата:** 2026-04-06  
**Формат документа:** ТЗ на разработку MVP внутреннего веб-приложения

---

## 1. Общая информация

### 1.1. Назначение

Система предназначена для автоматизированного формирования обучающих материалов на основе исходных файлов пользователя:

- видеофайлы вебинаров;
- презентации PPT/PPTX;
- PDF-документы;
- DOC/DOCX-документы.

### 1.2. Цель MVP

Пользователь должен иметь возможность:

1. создать проект;
2. загрузить до 5 файлов;
3. запустить обработку;
4. получить поэтапно сформированные результаты;
5. отредактировать результат каждого этапа;
6. подтвердить переход к следующему этапу;
7. скачать итоговые Markdown и JSON-артефакты.

### 1.3. Предметная область

Светопрозрачные конструкции.

---

## 2. Зафиксированные решения

1. Приложение внутреннее, без аутентификации.
2. Пользователи работают через один веб-интерфейс.
3. В одном проекте можно смешивать видео, презентации и документы.
4. Upload делается напрямую в S3-compatible storage Beget через multipart upload.
5. Resume upload после закрытия вкладки не требуется.
6. Редактирование результатов выполняется в обычном Markdown-редакторе.
7. Подтверждение этапа делается на том же экране, где открыт редактор.
8. LLM для MVP: OpenAI и OpenRouter.
9. Canonical job status model: `queued`, `processing`, `done`, `failed`.
10. Система рассчитана на небольшой внутренний контур:
   - до 5 пользователей;
   - до 100 генераций в месяц.
11. Имя проекта задается из GitHub-источника и не редактируется вручную.
12. Хранится только последняя подтвержденная версия результата этапа.

---

## 3. Границы MVP

### 3.1. Входит в MVP

1. Веб-интерфейс для загрузки файлов.
2. Прямая загрузка больших файлов в S3-compatible storage Beget из браузера.
3. Поддержка форматов:
   - MP4, MOV, AVI, MKV, WEBM;
   - PPT, PPTX;
   - PDF;
   - DOC, DOCX.
4. Очередь задач на обработку.
5. Видеообработка с использованием FFmpeg:
   - извлечение аудио;
   - нормализация аудиоформата для транскрибации.
6. Локальная транскрибация аудио на русском языке через `openai/whisper`.
7. Извлечение текста из PDF, PPT/PPTX, DOC/DOCX.
8. Очистка и нормализация извлеченного контента.
9. Поэтапная генерация:
   - `source_compiled`;
   - `course_outline`;
   - `course_content`;
   - `course_test`.
10. Возможность ручной корректировки результатов между этапами.
11. Отдельные Markdown- и JSON-файлы для каждого этапа.
12. Отображение статусов обработки в интерфейсе.
13. Пагинация списка проектов по 25 элементов.

### 3.2. Не входит в MVP

1. LMS-функциональность.
2. SCORM/xAPI.
3. Ролевая модель доступа.
4. Resume upload после закрытия браузера.
5. Email, Telegram и другие уведомления.
6. OCR и vision-анализ кадров видео.
7. Мобильное приложение.

## 4. Пользователь и доступ

### 4.1. Тип пользователя

На этапе MVP используется один внутренний тип пользователя без аутентификации.

### 4.2. Доступные действия

Пользователь может:

- создавать проекты;
- загружать файлы;
- запускать обработку;
- просматривать статусы;
- открывать и редактировать результаты этапов;
- подтверждать этапы;
- скачивать итоговые артефакты;
- просматривать список проектов с пагинацией.

---

## 5. Основной сценарий

1. Пользователь открывает веб-приложение.
2. Создает проект.
3. Выбирает локальные файлы на компьютере.
4. Файлы загружаются напрямую в S3-хранилище через браузер.
5. После успешной загрузки пользователь запускает обработку.
6. Система ставит задачи в очередь.
7. Для видео:
   - файл скачивается worker-сервисом;
   - из видео извлекается аудио;
   - аудио нормализуется;
   - выполняется транскрибация через `openai/whisper`.
8. Для документов:
   - выполняется извлечение текста из PDF/PPT/PPTX/DOC/DOCX.
9. Система объединяет и очищает исходный контент.
10. Система формирует `source_compiled`.
11. Пользователь редактирует и подтверждает результат.
12. Система формирует `course_outline`.
13. Пользователь редактирует и подтверждает план.
14. Система формирует `course_content`.
15. Пользователь редактирует и подтверждает материалы.
16. Система формирует `course_test`.
17. Пользователь редактирует и подтверждает тест.
18. Пользователь скачивает итоговые артефакты.

## 6. Функциональные требования

### 6.1. Загрузка файлов

Система должна:

1. обеспечивать выбор файлов через веб-интерфейс;
2. поддерживать загрузку больших файлов в S3-compatible storage Beget;
3. использовать multipart upload;
4. показывать прогресс загрузки;
5. выполнять ретраи частей при сетевых ошибках;
6. валидировать:
   - количество файлов;
   - размер файла;
   - допустимое расширение;
   - MIME type по возможности;
7. запрещать запуск обработки до завершения загрузки всех файлов проекта.

### 6.2. Управление проектами и задачами

Система должна:

1. создавать проект;
2. хранить метаданные проекта и файлов;
3. ставить обработку в очередь после подтверждения пользователя;
4. обеспечивать последовательное прохождение этапов;
5. хранить статусы jobs;
6. поддерживать повторный запуск неуспешного этапа;
7. отображать список проектов с пагинацией.

### 6.3. Видеообработка

Система должна:

1. скачивать видеофайл из S3 во временное рабочее пространство worker-сервиса;
2. проверять доступность и целостность файла;
3. запускать FFmpeg для извлечения аудиодорожки;
4. приводить аудио к нормализованному формату;
5. корректно обрабатывать ошибки неподдерживаемого или поврежденного медиафайла.

### 6.4. Транскрибация

Система должна:

1. использовать локально развернутый сервис на базе `openai/whisper`;
2. принимать подготовленный аудиофайл;
3. возвращать текст транскрибации;
4. возвращать сегменты/фрагменты при технической возможности;
5. сохранять результат как минимум в виде:
   - `raw_transcript.md`;
   - `raw_transcript.json`.

### 6.5. Извлечение текста из документов

Система должна:

1. извлекать текст из PDF;
2. извлекать текст из PPT/PPTX;
3. извлекать текст из DOC/DOCX;
4. объединять извлеченные данные в единый структурированный источник;
5. сохранять промежуточные результаты в JSON и Markdown.

### 6.6. Очистка и нормализация

Система должна:

1. удалять коммерческую и нерелевантную информацию по общему принципу;
2. удалять контактные данные, если они не относятся к содержанию обучения;
3. устранять технический шум и повторы;
4. нормализовывать заголовки, списки, абзацы и структуру;
5. готовить контент к генерации следующего этапа.

### 6.7. Генерация `source_compiled`

Система должна:

1. собирать очищенный исходный материал;
2. формировать промежуточный структурированный источник;
3. сохранять результат в Markdown и JSON.

### 6.8. Генерация `course_outline`

Система должна:

1. строить план курса на основе очищенного контента;
2. учитывать целевую аудиторию:
   - продажи;
   - услуги;
   - производство;
3. ограничивать структуру максимум 10 разделами;
4. формировать `course_outline.md` и `course_outline.json`.

### 6.9. Генерация `course_content`

Система должна:

1. генерировать материалы по утвержденному плану;
2. использовать профессиональный стиль без жаргона;
3. формировать понятную структуру разделов;
4. сохранять результат в `course_content.md` и `course_content.json`.

### 6.10. Генерация `course_test`

Система должна:

1. формировать тест по итоговым обучающим материалам;
2. создавать 10 вопросов;
3. создавать 3 варианта ответа на каждый вопрос;
4. указывать 1 правильный ответ;
5. сохранять результат в `course_test.md` и `course_test.json`.

### 6.11. Ручная корректировка

Система должна:

1. предоставлять пользователю возможность открыть промежуточный результат каждого этапа;
2. показывать Markdown-редактор;
3. сохранять отредактированный вариант;
4. запускать следующий этап только после подтверждения пользователя;
5. не запускать следующий этап автоматически.

### 6.12. Статусы

Система должна использовать каноническую модель job-статусов:

- `queued`
- `processing`
- `done`
- `failed`

На уровне UI дополнительно отображаются состояния проекта:

- `draft`
- `uploaded`
- `processing`
- `awaiting_review`
- `completed`
- `failed`

## 7. Требования к интерфейсу

### 7.1. Общие требования

Интерфейс должен быть веб-ориентированным и доступным из браузера на ПК.

### 7.2. Основные экраны

1. Список проектов с пагинацией.
2. Экран создания и загрузки файлов в проект.
3. Экран запуска обработки.
4. Экран просмотра статусов этапов.
5. Экран редактирования и подтверждения результата этапа.
6. Экран скачивания итоговых файлов.

### 7.3. Требования к UX загрузки

1. Пользователь не должен использовать консоль, отдельные утилиты или внешние сервисы.
2. Все действия по загрузке выполняются только в одном веб-интерфейсе.
3. Пользователь должен видеть:
   - прогресс загрузки файла;
   - процент выполнения;
   - ошибки загрузки;
   - итоговый статус файла.

## 8. Артефакты

### 8.1. Форматы

Для каждого этапа должны формироваться:

1. Markdown-файл для чтения человеком.
2. JSON-файл для машинной обработки и повторной сборки следующего этапа.

### 8.2. Обязательные артефакты

Минимальный набор:

- `source_compiled.md`
- `source_compiled.json`
- `course_outline.md`
- `course_outline.json`
- `course_content.md`
- `course_content.json`
- `course_test.md`
- `course_test.json`

Для видео дополнительно:

- `raw_transcript.md`
- `raw_transcript.json`

### 8.3. Требования к JSON

JSON должен быть:

- валидным;
- пригодным для повторной сборки следующего этапа;
- структурированным и документированным на уровне схемы проекта.

## 9. Нефункциональные требования

### 9.1. Производительность

1. Система должна поддерживать загрузку файлов размером до 2 ГБ.
2. Система должна поддерживать пакет до 5 файлов.
3. Система должна выполнять фоновую обработку без блокировки интерфейса.
4. Система должна корректно обрабатывать длительные задачи.

### 9.2. Надежность

1. Ошибка одного этапа не должна приводить к потере уже загруженных файлов.
2. Ошибка одной части multipart upload не должна требовать повторной загрузки всего файла.
3. Система должна вести журналы ошибок обработки.
4. Система должна позволять повторить упавший этап.

### 9.3. Безопасность

1. Приложение разворачивается на сервере заказчика.
2. Подключение к S3, PostgreSQL и Redis выполняется по переменным окружения.
3. Секреты не должны храниться в исходном коде.
4. Необходимо ограничить загрузку по размеру и типам файлов.
5. Необходимо настроить CORS для загрузки в S3-compatible storage.
6. Доступ к приложению должен быть закрыт от неавторизованных пользователей на уровне инфраструктуры или сетевого контура.

### 9.4. Поддерживаемость

1. Система должна быть контейнеризирована.
2. Основные сервисы приложения должны собираться и обновляться независимо от внешних Postgres, Redis и S3.
3. Конфигурация должна выполняться через env-переменные.

### 9.5. Очистка артефактов

1. Очистка S3 выполняется раз в неделю.
2. Удалять можно только артефакты проектов, для которых уже собран полный пакет:
   - `course_outline`;
   - `course_content`;
   - `course_test`.
3. До сборки полного пакета исходные и промежуточные артефакты не удаляются.
4. Для полного пакета можно дополнительно применять срок хранения, но только при соблюдении условия полноты пакета.

## 10. Интеграции

### 10.1. S3-compatible storage Beget

Система должна использовать внешнее S3-хранилище Beget для:

- хранения загруженных исходных файлов;
- хранения промежуточных и итоговых артефактов;
- доступа по S3 API.

### 10.2. PostgreSQL

Система должна использовать внешний PostgreSQL для:

- хранения сущностей проекта;
- хранения статусов;
- хранения метаданных файлов и задач;
- хранения ссылок на артефакты.

### 10.3. Redis

Система должна использовать внешний Redis для очередей задач.

### 10.4. LLM-провайдеры

Система должна иметь возможность обращения к:

- OpenAI;
- OpenRouter.

### 10.5. Local Whisper service

Система должна обращаться к локально развернутому сервису транскрибации на базе `openai/whisper`.

## 11. Развертывание

### 11.1. Среда размещения

1. Система разворачивается на арендованном сервере заказчика в Beget.
2. Деплой выполняется через Dokploy.

### 11.2. Состав основного приложения

В составе основного деплоя должны быть:

- frontend;
- backend API;
- worker;
- transcription service.

### 11.3. Поведение при redeploy

1. Повторный деплой приложения не должен приводить к удалению пользовательских данных в PostgreSQL, Redis и S3.
2. Stateful-данные не должны храниться внутри контейнеров приложения.
3. Подключения к внешним сервисам должны выполняться по строкам подключения и ключам доступа через env.

## 14. Критерии приемки

Проект считается соответствующим ТЗ, если выполнены все условия:

1. Пользователь может через веб-интерфейс загрузить до 5 файлов, включая видео до 2 ГБ каждый.
2. Загрузка выполняется без использования CLI, сторонних десктопных программ и внешних ручных сервисов.
3. После загрузки система может запустить обработку в фоне.
4. Видео проходит через этап извлечения аудио.
5. Аудио транскрибируется локальным сервисом `openai/whisper`.
6. Документы PDF/PPT/PPTX/DOC/DOCX проходят извлечение текста.
7. Система формирует как минимум следующие этапы:
   - `source_compiled`;
   - `course_outline`;
   - `course_content`;
   - `course_test`.
8. Между этапами пользователь может вручную редактировать результат.
9. Для каждого этапа формируются Markdown и JSON файлы.
10. Пользователь видит статус обработки в интерфейсе.
11. При redeploy приложения данные во внешних PostgreSQL, Redis и S3 не теряются.
