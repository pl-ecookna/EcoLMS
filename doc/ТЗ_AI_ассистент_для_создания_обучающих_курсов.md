# Техническое задание
## Проект: AI-ассистент для создания обучающих курсов

**Версия:** 1.0  
**Дата:** 2026-04-06  
**Формат документа:** ТЗ на разработку MVP внутреннего веб-приложения

---

## 1. Общая информация о проекте

### 1.1. Наименование проекта
AI-ассистент для создания обучающих курсов по материалам заказчика.

### 1.2. Назначение системы
Система предназначена для автоматизированного формирования обучающих материалов на основе исходных файлов пользователя:
- видеофайлов вебинаров;
- презентаций PPT/PPTX;
- технической документации PDF;
- документов DOC/DOCX.

### 1.3. Цель проекта
Создать внутренний веб-инструмент, который позволяет пользователю:
1. загрузить исходные материалы;
2. запустить обработку;
3. получить поэтапно сформированные результаты в виде Markdown-файлов и JSON-артефактов;
4. при необходимости вручную скорректировать результаты отдельных этапов;
5. собрать итоговый обучающий курс и тест.

### 1.4. Предметная область
Светопрозрачные конструкции.

### 1.5. Исходные требования заказчика
Базовые требования проекта включают:
- обработку презентаций, записей вебинаров, технической документации;
- извлечение информации из материалов;
- создание структуры курса с ограничением не более 10 разделов;
- поэтапную генерацию материалов: план обучения → обучающие материалы → тест;
- удаление из исходных материалов нерелевантной информации;
- формирование теста на 10 вопросов, по 3 варианта ответа, 1 правильный ответ;
- поддержку целевой аудитории: продажи, услуги, производство.

## 2. Границы MVP

### 2.1. Входит в MVP
1. Веб-интерфейс для загрузки файлов.
2. Поддержка прямой загрузки больших файлов в S3-совместимое хранилище Beget из браузера.
3. Поддержка форматов:
   - MP4, MOV, AVI, MKV, WEBM (видео);
   - PPT, PPTX;
   - PDF;
   - DOC, DOCX.
4. Очередь задач на обработку.
5. Видеообработка с использованием FFmpeg:
   - извлечение аудио из видео;
   - нормализация аудиоформата для транскрибации.
6. Локальная транскрибация аудио на русском языке с использованием `openai/whisper`.
7. Извлечение текста из PDF, PPT/PPTX, DOC/DOCX.
8. Очистка и нормализация извлеченного контента.
9. Полуавтоматический сценарий генерации:
   - этап 1: черновой структурированный источник;
   - этап 2: план курса;
   - этап 3: обучающие материалы;
   - этап 4: тест.
10. Возможность ручной корректировки результатов между этапами.
11. Формирование отдельных Markdown-файлов и JSON-файлов для каждого этапа.
12. Отображение статусов обработки в интерфейсе.

### 2.2. Не входит в MVP
1. LMS-функциональность.
2. SCORM/xAPI.
3. Многопользовательская ролевая модель.
4. История проектов и переиспользование загруженных материалов.
5. Уведомления по email, Telegram и др.
6. Извлечение текста со слайдов из видео.
7. Полноценный resume upload после закрытия вкладки/браузера.
8. Распознавание и анализ изображений, схем и таблиц из кадров видео.
9. Мобильное приложение.

## 3. Пользователи системы

### 3.1. Тип пользователя
На этапе MVP поддерживается **один тип пользователя**.

### 3.2. Права пользователя
Пользователь может:
- войти в систему;
- загрузить до 5 файлов за одну сессию загрузки;
- запускать обработку;
- просматривать статусы;
- открывать результаты этапов;
- редактировать результаты между этапами;
- подтверждать переход к следующему этапу;
- скачивать итоговые артефакты.

## 4. Ограничения и допущения

### 4.1. Ограничения по загрузке
1. Максимальный размер одного файла: **2 ГБ**.
2. Максимальное количество файлов в одном наборе: **5**.
3. Рекомендуемая максимальная длительность одного видео: **до 3 часов**.
4. Поддерживается базовый режим устойчивости загрузки:
   - повтор неудачно загруженных частей в рамках текущей браузерной сессии;
   - без обязательного восстановления загрузки после закрытия вкладки.

### 4.2. Ограничения по языку
1. В MVP поддерживается **только русский язык** для транскрибации и генерации.
2. Все пользовательские интерфейсы и результирующие материалы формируются на русском языке.

### 4.3. Ограничения по результату
1. Результаты выдаются в Markdown и JSON.
2. Один этап — отдельный Markdown-файл и отдельный JSON-файл.
3. Система не обязана сохранять историю проектов после завершения работы пользователя, кроме технически необходимого времени хранения артефактов.

## 5. Основной пользовательский сценарий

### 5.1. Сценарий работы
1. Пользователь открывает веб-приложение.
2. Пользователь выбирает локальные файлы на компьютере.
3. Файлы загружаются напрямую в S3-хранилище через веб-интерфейс.
4. После успешной загрузки пользователь запускает обработку.
5. Система ставит задачи в очередь.
6. Для видео:
   - файл скачивается worker-сервисом;
   - из видео извлекается аудио;
   - аудио нормализуется;
   - выполняется транскрибация через `openai/whisper`.
7. Для документов:
   - выполняется извлечение текста из PDF/PPT/PPTX/DOC/DOCX.
8. Система объединяет и очищает исходный контент.
9. Система формирует черновой структурированный источник.
10. Пользователь просматривает и при необходимости редактирует результат.
11. Система формирует план курса.
12. Пользователь просматривает и при необходимости редактирует план.
13. Система формирует обучающие материалы.
14. Пользователь просматривает и при необходимости редактирует материалы.
15. Система формирует тест.
16. Пользователь просматривает и при необходимости редактирует тест.
17. Пользователь скачивает итоговые артефакты.

## 6. Функциональные требования

## 6.1. Модуль загрузки файлов
Система должна:
1. обеспечивать выбор файлов через веб-интерфейс;
2. поддерживать загрузку больших файлов в S3-compatible storage Beget;
3. использовать multipart upload;
4. показывать прогресс загрузки;
5. выполнять базовые ретраи частей при сетевых ошибках;
6. валидировать:
   - количество файлов;
   - размер файла;
   - допустимое расширение;
   - MIME type по возможности;
7. запрещать запуск обработки до завершения загрузки всех необходимых файлов.

## 6.2. Модуль управления задачами
Система должна:
1. создавать задания на обработку после подтверждения пользователем;
2. ставить задания в очередь;
3. обеспечивать последовательное прохождение этапов;
4. хранить статусы задач;
5. поддерживать повторный запуск неуспешного этапа;
6. разделять этапы обработки на независимые job-операции.

## 6.3. Модуль видеообработки
Система должна:
1. скачивать видеофайл из S3 во временное рабочее пространство worker-сервиса;
2. проверять доступность и целостность файла;
3. запускать FFmpeg для извлечения аудиодорожки;
4. приводить аудио к нормализованному формату, пригодному для транскрибации;
5. сохранять промежуточные технические артефакты по правилам системы хранения;
6. корректно обрабатывать ошибки неподдерживаемого или поврежденного медиафайла.

## 6.4. Модуль транскрибации
Система должна:
1. использовать локально развернутый сервис на базе `openai/whisper`;
2. принимать на вход подготовленный аудиофайл;
3. возвращать текст транскрибации;
4. возвращать сегменты/фрагменты транскрибации при технической возможности реализации;
5. сохранять результат как минимум в виде:
   - `raw_transcript.md`;
   - `raw_transcript.json`.

## 6.5. Модуль извлечения текста из документов
Система должна:
1. извлекать текст из PDF;
2. извлекать текст из PPT/PPTX;
3. извлекать текст из DOC/DOCX;
4. объединять извлеченные данные в единый структурированный источник;
5. сохранять промежуточные результаты в JSON и Markdown.

## 6.6. Модуль очистки и нормализации контента
Система должна:
1. удалять коммерческую и нерелевантную информацию;
2. удалять контактные данные, если они не относятся к содержанию обучения;
3. устранять технический шум и повторы;
4. нормализовывать заголовки, списки, абзацы и структуру;
5. готовить контент к следующему этапу генерации.

## 6.7. Модуль генерации плана курса
Система должна:
1. строить план курса на основе очищенного контента;
2. учитывать целевую аудиторию:
   - продажи;
   - услуги;
   - производство;
3. ограничивать структуру максимум 10 разделами;
4. формировать результат в виде:
   - `course_outline.md`;
   - `course_outline.json`.

## 6.8. Модуль генерации обучающих материалов
Система должна:
1. генерировать материалы по утвержденному плану;
2. использовать профессиональный стиль без жаргона;
3. формировать понятную структуру разделов;
4. сохранять результат в виде:
   - `course_content.md`;
   - `course_content.json`.

## 6.9. Модуль генерации теста
Система должна:
1. формировать тест по итоговым обучающим материалам;
2. создавать 10 вопросов;
3. создавать 3 варианта ответа на каждый вопрос;
4. задавать 1 правильный ответ;
5. сохранять результат в виде:
   - `course_test.md`;
   - `course_test.json`.

## 6.10. Модуль ручной корректировки
Система должна:
1. предоставлять пользователю возможность открыть промежуточный результат каждого этапа;
2. сохранять отредактированный вариант;
3. запускать следующий этап на основе подтвержденной редакции;
4. не запускать следующий этап автоматически без подтверждения пользователя.

## 6.11. Модуль статусов
Система должна отображать статусы:
- `uploading`
- `uploaded`
- `queued`
- `preprocessing`
- `transcribing`
- `extracting_documents`
- `normalizing`
- `awaiting_review_source`
- `generating_outline`
- `awaiting_review_outline`
- `generating_content`
- `awaiting_review_content`
- `generating_test`
- `awaiting_review_test`
- `completed`
- `failed`

## 7. Требования к интерфейсу

### 7.1. Общие требования
Интерфейс должен быть веб-ориентированным и доступным из браузера на ПК.

### 7.2. Основные экраны
1. Экран загрузки файлов.
2. Экран списка выбранных файлов и статуса загрузки.
3. Экран запуска обработки.
4. Экран просмотра статусов этапов.
5. Экран просмотра и редактирования результатов этапа.
6. Экран скачивания итоговых файлов.

### 7.3. Требования к UX загрузки
1. Пользователь не должен использовать консоль, отдельные утилиты или внешние сервисы.
2. Все действия по загрузке выполняются только в одном веб-интерфейсе.
3. Пользователь должен видеть:
   - прогресс загрузки файла;
   - процент выполнения;
   - ошибки загрузки;
   - итоговый статус файла.

## 8. Требования к данным и артефактам

## 8.1. Артефакты этапов
Для каждого этапа должны формироваться:
1. Markdown-файл для чтения человеком.
2. JSON-файл для машинной обработки и повторной сборки следующего этапа.

### 8.2. Обязательные артефакты
Минимальный набор:
- `source_compiled.md`
- `source_compiled.json`
- `course_outline.md`
- `course_outline.json`
- `course_content.md`
- `course_content.json`
- `course_test.md`
- `course_test.json`

Для видео дополнительно:
- `raw_transcript.md`
- `raw_transcript.json`

### 8.3. Требования к JSON
JSON должен быть:
- валидным;
- пригодным для повторной сборки следующего этапа;
- структурированным и документированным на уровне схемы проекта.

## 9. Нефункциональные требования

## 9.1. Производительность
1. Система должна поддерживать загрузку файлов размером до 2 ГБ.
2. Система должна поддерживать пакет до 5 файлов.
3. Система должна выполнять фоновую обработку без блокировки веб-интерфейса.
4. Система должна корректно обрабатывать длительные задачи.

## 9.2. Надежность
1. Ошибка одного этапа не должна приводить к потере уже загруженных файлов.
2. Ошибка одной части multipart upload не должна требовать повторной загрузки всего файла.
3. Система должна вести журналы ошибок обработки.
4. Система должна позволять повторить упавший этап.

## 9.3. Безопасность
1. Приложение разворачивается на сервере заказчика.
2. Подключение к S3, PostgreSQL и Redis выполняется по переменным окружения.
3. Секреты не должны храниться в исходном коде.
4. Необходимо ограничить загрузку по размеру и типам файлов.
5. Необходимо настроить CORS для загрузки в S3-compatible storage.
6. Доступ к приложению должен быть закрыт от неавторизованных пользователей.

## 9.4. Поддерживаемость
1. Система должна быть контейнеризирована.
2. Основные сервисы приложения должны собираться и обновляться независимо от внешних Postgres, Redis и S3.
3. Конфигурация должна выполняться через env-переменные.

## 10. Интеграции

### 10.1. S3-compatible storage Beget
Система должна использовать внешнее S3-хранилище Beget для:
- хранения загруженных исходных файлов;
- хранения промежуточных и итоговых артефактов;
- доступа по S3 API.

### 10.2. PostgreSQL
Система должна использовать внешний PostgreSQL для:
- хранения сущностей проекта;
- хранения статусов;
- хранения метаданных файлов и задач;
- хранения ссылок на артефакты.

### 10.3. Redis
Система должна использовать внешний Redis для очередей задач.

### 10.4. LLM-провайдер
Система должна иметь возможность обращения к внешнему LLM API для этапов нормализации и генерации обучающих материалов.

### 10.5. Local Whisper service
Система должна обращаться к локально развернутому сервису транскрибации на базе `openai/whisper`.

---

## 11. Требования к развертыванию

### 11.1. Среда размещения
1. Система разворачивается на арендованном сервере заказчика в Beget.
2. Деплой выполняется через Dokploy.

### 11.2. Размещение инфраструктуры
Отдельно от основного стека приложения размещаются:
- PostgreSQL;
- Redis;
- S3-compatible storage (внешний сервис Beget).

### 11.3. Состав основного приложения
В составе основного деплоя должны быть:
- frontend;
- backend API;
- worker;
- transcription service на базе `openai/whisper`.

### 11.4. Поведение при redeploy
1. Повторный деплой приложения не должен приводить к удалению пользовательских данных в PostgreSQL и Redis.
2. Stateful-данные не должны храниться внутри контейнеров приложения.
3. Подключения к внешним сервисам должны выполняться по строкам подключения и ключам доступа через env.

## 14. Критерии приемки

Проект считается соответствующим ТЗ, если выполнены все условия:

1. Пользователь может через веб-интерфейс загрузить до 5 файлов, включая видео до 2 ГБ каждый.
2. Загрузка выполняется без использования CLI, сторонних десктопных программ и внешних ручных сервисов.
3. После загрузки система может запустить обработку в фоне.
4. Видео проходит через этап извлечения аудио.
5. Аудио транскрибируется локальным сервисом `openai/whisper`.
6. Документы PDF/PPT/PPTX/DOC/DOCX проходят извлечение текста.
7. Система формирует как минимум следующие этапы:
   - структурированный источник;
   - план курса;
   - обучающие материалы;
   - тест.
8. Между этапами пользователь может вручную редактировать результат.
9. Для каждого этапа формируются Markdown и JSON файлы.
10. Пользователь видит статус обработки в интерфейсе.
11. При redeploy приложения данные во внешних Postgres, Redis и S3 не теряются.
